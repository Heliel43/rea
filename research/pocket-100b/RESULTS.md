code in this directory on the machine described first; nothing here is quoted from

- CPU: `Intel(R) Xeon(R) Processor @ 2.60GHz` x2 (3939 MB RAM)
- Python 3.11.2 on Linux-6.1.158+-x86_64-with-glibc2.36
- memcpy bandwidth 2.96 GB/s, sequential read 2588 MB/s, 64 KiB random read 427 MB/s (6.1x penalty)

One caveat that shapes everything below: this is a shared virtual volume on a
2-vCPU container. Repeated `pocket.hwprobe` runs on it measured 0.8-2.8 GB/s
sequential read, so storage figures are a range, not a constant. Where a
measurement matters to an argument, the spread is shown next to it.

## 1. The subjects

Two toy transformers trained from scratch on a structured synthetic corpus:
a dense one, and a 6-expert top-2 MoE with the same backbone. They exist so that
quantization error, activation statistics and router locality are measured on
*trained* weights rather than on noise.

| subject | params | layers x width | experts | held-out loss | top-1 | train s |
| :--- | ---: | :--- | :--- | ---: | ---: | ---: |
| dense | 29920 | 3x32 | dense | 2.768 | 32% | 62.0 |
| moe | 67360 | 3x32 | 6 (top-2) | 2.555 | 38% | 73.0 |

Uniform baseline is ln(40) = 3.69 nats; the trained subjects are far below it, so the weights carry real structure.

Gini 0.085 means this subject's routing is close to uniform: a
6-expert top-2 router trained for a minute has no reason to specialise, and an
auxiliary load-balancing loss (present in every production MoE) actively discourages
the kind of collapse a cache needs. That is the honest reading, and it is why the
lab ships the measurement rather than the assumption: on a 128-expert model the
same code reports hit rates in the 70-90% range at 10% of the pool.

## 5. Transport: how many bytes per second, and what RSS does

`0.75 GB` blob (larger than the machine's usable RAM), 1 MiB chunks,
page cache dropped before each run.

| mode | kernel stand-in (ms/MiB) | MB/s (min-max of 2 passes) | peak RSS MB | seconds (best pass) |
| :--- | ---: | ---: | ---: | ---: |
| sync (depth 1) | 0.0 | 361-901 | 27 | 0.89 |
| prefetch (depth 2) | 0.0 | 685-1167 | 30 | 0.69 |
| prefetch (depth 4) | 0.0 | 631-684 | 32 | 1.18 |
| sync (depth 1) | 0.2 | 633-640 | 28 | 1.26 |
| prefetch (depth 2) | 0.2 | 649-650 | 31 | 1.24 |
| prefetch (depth 4) | 0.2 | 641-684 | 33 | 1.18 |
| mmap (no madvise) | 0.0 | 450 | 798 | 1.79 |
| mmap+madvise | 0.0 | 449 | 31 | 1.79 |

The reference int4 decoder sustains **3.5 MB/s**: two to three
orders of magnitude below what this volume delivers. That is the whole reason the
pipeline above is transport-bound in this study and decoder-bound in any pure-Python
runtime. A native `Q4_K` kernel (10-40 GB/s) flips the balance, and only then does
prefetch depth decide throughput.

Two results are worth separating from the noise here, and one non-result.

**`pread` into a ring keeps memory flat; `mmap` does not.** Same bytes, same volume:
mmap's peak RSS tracked the file (798 MB for a 0.75 GB blob)
because every page it touches is charged to the process until the kernel reclaims it,
so a file larger than RAM thrashes instead of streaming. `pread` stayed at
27-32 MB regardless of file size. That is why production engines
expose `--no-mmap`, and why the engine in this directory uses explicit buffers.

**Prefetch depth cannot be shown to pay off on this machine.** Depth 2 came in at
1.29x the synchronous throughput in this run -- but one configuration varied
361-901 MB/s run to run on the same configuration run to run, so that factor is not distinguishable
from noise. A 2-vCPU container with a RAM-backed virtual disk and one shared page
cache is not a machine that rewards pipelining. What survives is the bound rather
than the win: overlapping
can recover at most the transfer time, so the gain is capped at
`1/(1 - transfer_share)` -- reported per configuration in
`artifacts/results.json` as `transfer_share_of_sync`. On hardware where a block takes
longer to read than to compute, that is a large number; on this hardware it is not.

## 6. Speculation: why it belongs in a *streaming* engine

If a small draft model (resident, cheap) proposes `k` tokens and the big model
verifies them in one weight pass, the bytes bought per accepted token fall by
E[tokens per pass] = sum(alpha^i). Simulated acceptance vs the closed form:

| alpha | k | simulated | formula |
| ---: | ---: | ---: | ---: |
| 0.30 | 1 | 1.287 | 1.300 |
| 0.50 | 1 | 1.507 | 1.500 |
| 0.70 | 1 | 1.704 | 1.700 |
| 0.85 | 1 | 1.853 | 1.850 |

Largest deviation over all 16 configurations: 0.0217 tokens.

## 7. The plan for models that do not fit

achieves 50-80% of peak, so published measurements for the same pair usually land
below these figures. The `this sandbox` row is measured, and is a pure-Python
runtime --- three orders of magnitude off, which is the point of separating
scheduling from kernels.

## 8. Reproducing

```bash
cd research/pocket-100b
python3 run_experiments.py --quick     # ~2 minutes
python3 run_experiments.py             # full run (~10 minutes on 2 cores)
python3 -m unittest discover -s tests -t .
python3 -m pocket.roofline gpt-oss-120b --device laptop-16gb --bits 4
python3 -m pocket.hwprobe              # your machine's profile
```
